# PEKA v0.1.4 — Design

Four features, released together:

1. **Project scoping.** Memories carry the project(s) they belong to. Each session sees
   global memories plus the current project's memories in full; other projects appear as
   one line each.
2. **Project-aware skill lifecycle.** A project skill's stale/archive clock only runs on
   days its project is actually worked on, so rarely used procedures (deploys) are not
   archived just because the project was idle.
3. **Learning notices.** The user can see what PEKA learned: a weekly one-line summary
   by default, or a line after every save, plus `/peka:status log` for the details.
4. **Stale memory check.** The curator is told which memories mention local paths that
   no longer exist.

## Why

Observed in a real store after three days: nearly every memory and skill belongs to one
project (`abqary-*`, `wajom-*`, `sihipam-*`), yet all of them load in every session. As
the store grows, `MEMORY.md` approaches Claude Code's ~200-line load limit and the skill
list gets noisier. Deploy skills are used once every few weeks (`wajom-portal-deploy`:
0 uses), so the calendar-based "archived after 30 days unused" rule will retire exactly
the skills that are most expensive to relearn. PEKA saves without approval, so it should
also show what it saved.

## Constraints

- `MEMORY.md` is loaded by Claude Code itself (first ~200 lines), not by PEKA. PEKA
  controls its content and can add context through the SessionStart hook, nothing more.
- Skills are linked into `~/.claude/skills`, which every running session shares. Hiding a
  skill per session would mean writing into each repo's `.claude/skills`, which PEKA does
  not do. Skills stay globally visible; their project tag drives lifecycle and grouping.
- Hooks must never fail the session; errors go to `state/peka.log`.
- Zero npm dependencies, Node ≥ 18, no network.

## 1. Project scoping

### Project identity (`scripts/lib/project.mjs`)

`projectOf(cwd)`:

1. Run `git rev-parse --path-format=absolute --git-common-dir` in `cwd` (timeout 2 s).
   If it succeeds, the project is the basename of the directory containing that git dir.
   Using the common dir means a worktree such as `abqary-new/.worktrees/feat-x` still
   resolves to `abqary-new`.
2. Otherwise the project is `basename(cwd)`.
3. If `cwd` is missing, is the home directory, or is the filesystem root, there is no
   project (`null`): the session sees global memories only.

Project names are normalized to `[a-z0-9._-]`, lowercase; other characters become `-`.

The session's project is computed once at SessionStart and stored in the session state
file, so other hooks do not spawn git.

### Tagging

Memories and skills may carry `metadata.project`: one name, or several separated by
commas. No tag means global.

```yaml
---
name: wajom-build-before-push
description: portal and client: Node 20 npm run build, then git add . incl. artifacts, then push
metadata:
  type: feedback
  project: wajom-portal, wajom-client
---
```

`frontmatter.mjs` learns to read `project` (top level or under `metadata:`) and returns it
as an array via a helper `projectsOf(fields)`.

### Generated index (`scripts/lib/memory-index.mjs`)

Memory files are the only source of truth. `buildIndex(d)` reads every `memory/*.md`
except `MEMORY.md` and writes:

`memory/MEMORY.md`:

```markdown
<!-- Generated by PEKA from the memory files. Edits here are overwritten. -->
- [user-writes-indonesian](user-writes-indonesian.md) — reply in Indonesian; code and commits stay English
- [show-images-inline-no-preview-server](show-images-inline-no-preview-server.md) — generated images go inline …

## Projects
- abqary-new: 2 memories, see [projects/abqary-new.md](projects/abqary-new.md)
- wajom-portal: 2 memories, see [projects/wajom-portal.md](projects/wajom-portal.md)
```

`memory/projects/<project>.md`: a heading and one line per memory of that project, linking
`../<file>.md`. A memory tagged with several projects appears in each.

Rules:

- Entry line: `- [<name>](<file>) — <description>`; description clipped to 150
  characters; `name` falls back to the file name, description to `(no description)`.
- Order: global entries sorted by type (`feedback`, `user`, `project`, `reference`,
  other), then name. Projects sorted by name.
- Line budget: `MEMORY.md` stays at or under 190 lines. If global entries do not fit, the
  overflow is left out and a final line says `- … N more global memories, run
  /peka:status`. The overflow count is recorded for the curator report.
- `memory/projects/` holds only generated files; sub-indexes for projects with no
  memories left are removed.
- Writes are skipped when the content is unchanged (keeps git history clean). Any error is
  logged and the previous index is left in place.

When `buildIndex` runs:

- SessionStart.
- SubagentStop of any PEKA agent, before the auto-commit.
- PostToolUse when the main agent writes a memory file (guard `classify` already reports
  `kind === "memory"`), including a direct edit of `MEMORY.md`, which is overwritten.

### Session brief

`sessionBrief(d, project)` appends, when the session has a project with memories:

```
Current project: abqary-new. Its memories (read the ones that apply before working):
- [abqary-commit-push-deploy-without-confirmation](…) — …
```

When the project has no memories, it appends `Current project: <name> (no memories yet).
Tag project-specific memories with metadata.project: <name>.` Without a project, nothing
is appended. The brief is also returned after compaction, as today.

### Agents

Reviewer, learner, and curator prompts change:

- Set `metadata.project` on project-specific memories and skills, using the project name
  given in the prompt (`Project: <name>` line, `none` when there is none). PEKA fills it
  from the session state: the Stop hook for the reviewer, `peka learn --session <id>` for
  the learner. The curator gets `Project: none`.
- Do not edit `MEMORY.md` or `memory/projects/`; PEKA rebuilds them.
- The curator additionally tags untagged memories and skills that clearly belong to a
  known project (listed in its report).

Main-session Claude Code may still append to `MEMORY.md` following its built-in memory
instructions; the next rebuild replaces the line with the generated one, so nothing is
lost as long as the memory file exists.

### Migration

- Untagged memories stay global, so upgrading changes nothing until tags are added.
- The first SessionStart after upgrading rebuilds `MEMORY.md` in the generated format.
  Human-written titles in the old index are replaced by memory names.
- `peka audit` gains a section: "Memories and skills that mention a known project but have
  no project tag", where known projects are those in `state/projects.json`. Approved
  fixes go to the learner like other audit fixes.
- The curator tags the same candidates on its weekly run.

## 2. Project-aware skill lifecycle

### Activity log (`state/projects.json`)

```json
{ "abqary-new": { "activeDays": ["2026-10-12", "2026-10-14"] } }
```

At SessionStart and UserPromptSubmit (main agent) the session's project gets today's
local date (`YYYY-MM-DD`) added if missing. Each project keeps its last 120 active days.
Written with `writeJsonAtomic`; last writer wins across parallel sessions (one missed
day at worst, acceptable).

### Lifecycle rule (`applyLifecycle`)

For each unpinned skill, age is computed from `lastUsed ?? created`:

- **Global skill:** calendar days since then, as today.
- **Project skill:** number of distinct active days of any of its projects strictly after
  that date. A project that never appears in `projects.json` contributes 0, so the skill
  is never marked stale by age (the curator report lists it).

Thresholds are unchanged: stale at 14, archived at 30. For a project worked on every day
the result is identical to the calendar rule.

`applyLifecycle` reads skill project tags from frontmatter each run (cheap: a handful of
files, once a day).

### Status and report

- `peka status` groups skills under their project headings (global first) and shows
  "N active days since last use" for project skills.
- The curator report adds columns `Project` and `Age (days)` and a list of project tags
  with no recorded activity.

## 3. Learning notices

### Option

New `userConfig` key `learning_notice` in `plugin.json`: `weekly` (default), `each`, or
`off`. Read in `config.mjs` as `learningNotice`, invalid values fall back to `weekly`.

### Change summary (`scripts/lib/changes.mjs`)

Built from the `~/.peka` git history, so it reflects what was actually written, not what
an agent claims.

`changesSince(home, ref)` runs `git log --name-status --format=%H%x09%cI%x09%s <range>`
and maps paths to items:

| Path | Item |
|---|---|
| `memory/<f>.md` (not `MEMORY.md`) | memory `<f>` |
| `skills/<name>/…` | skill `<name>` |
| `archive/…` | ignored (the matching delete above is reported as archived) |
| `MEMORY.md`, `memory/projects/…`, anything else | ignored |

Status per item: `A` → added, `M` → updated, `D` (or the source side of `R`) → archived,
since PEKA never deletes. An item touched by several commits is reported once with its
latest status, except added-then-updated stays "added".

`summarize(changes)` produces one line, for example
`+2 memories, 1 skill updated, 1 skill archived` (empty when nothing changed).

### `each`

In `subagentStop`, after `commit()`: if a new commit was made, summarize that commit's
changes with names:
`PEKA: memory wajom-build-before-push updated; skill abqary-deploy added.`
Returned as `systemMessage`. No commit (nothing changed or git unavailable) → no message.

### `weekly`

`state/notice.json` holds `lastNoticeAt` and `lastNoticeCommit`. At SessionStart:

- First run: seed both, no message.
- If `lastNoticeAt` is at least 7 days old: summarize commits after `lastNoticeCommit`. If
  there are changes, return `systemMessage`
  `PEKA this week: +3 memories, 1 skill updated, 2 archived. Details: /peka:status log`.
  Update both fields either way.
- If `lastNoticeCommit` no longer exists in the history, re-seed without a message.

### `off`

No messages. `/peka:status log` still works.

### `/peka:status log [days]`

New CLI subcommand `peka log [days]` (default 7, max 365) and a `log` branch in
`skills/status/SKILL.md` (plus its `allowed-tools` entry). Prints each commit in range,
newest first: date, short hash, message, then its items with status. Ends with how to
undo: `git -C <PEKA home> revert <hash>`.

### Without git

If `~/.peka` has no git repository or `auto_commit` is off, notices are silent and
`peka log` explains that history needs git and auto-commit on.

## 4. Stale memory check

`writeCuratorReport` gains a section "Memories mentioning missing local paths".

- For each memory file body (not frontmatter), extract path-like tokens: absolute paths
  (`/a/b…`, at least two segments) and home paths (`~/a…`). Skip tokens preceded by
  `://` or `@` (URLs, `user@host:path`), and tokens inside a line that mentions `ssh`.
- Expand `~`, strip trailing punctuation (`.,;:)'"\``), and check `fs.existsSync`.
- List `file.md: /missing/path` for each missing one, at most 50 lines.

The curator prompt explains that a missing path may belong to another machine; fix or
retire a memory only when it clearly describes this machine and the path is gone.

The report also lists the index overflow count from section 1.

## Error handling

- Project detection failure → `null` project; the session behaves as before 0.1.4.
- Index build failure → logged; old index kept.
- Corrupt `projects.json` / `notice.json` → treated as empty (existing `readJson`
  fallback); notices re-seed without a message.
- Any git failure in notices → no message, logged.

## Testing

`node --test`, one suite per new module plus handler coverage, using temp `PEKA_HOME`
dirs and temp git repos as the existing tests do:

- `project.test.mjs`: repo root, subdirectory, worktree, non-repo dir, home dir,
  name normalization.
- `memory-index.test.mjs`: global vs project entries, multi-project memory, ordering,
  clipping, 190-line overflow line, stale sub-index removal, unchanged content not
  rewritten.
- `changes.test.mjs`: add/update/archive mapping, rename to archive, ignored paths,
  summary wording, empty range.
- `skills.test.mjs`: project skill not aged on idle days, aged on active days,
  multi-project skill, unknown project never stale, global rule unchanged; report
  sections.
- `handlers.test.mjs`: brief includes current project memories; index rebuilt on
  memory write and SubagentStop; `each` message after commit; `weekly` seeding and
  7-day message; `off` silent; activity marked on prompt.
- `cli.test.mjs`: `log`, grouped `status`, new audit section.
- `plugin-files.test.mjs`: `learning_notice` option and version bump.
